# 2FA 更换与恢复

已有 2FA 的账号可在原任务行点击“更换 2FA”，或勾选账号后点击“批量更换 2FA”。确认后依次验证登录、移除旧验证器、申请新密钥、激活并核实新验证器、加密保存和读回新密钥。批量操作跳过不符合条件的账号，各账号结果显示在任务行

未启用的账号继续使用“设置 2FA”。更换需要通过账号正常登录验证；没有有效旧密钥时可能需要手动输入当前验证码，不提供绕过身份验证的能力。操作不退出其他设备，也不自动重新授权或同步 CPR

## 中断后的处理

点击任务行的“核对恢复 2FA”。请求前的操作阶段与返回的新密钥保存在加密记录中，恢复先查询远端状态；只有证据明确的阶段才继续

| 保存的阶段 | 恢复行为 |
| --- | --- |
| 尚未发起移除 | 结束本次未执行的操作，允许重新确认更换 |
| 移除结果未知 | 查询旧验证器；仍存在则结束本次操作，不重新移除；确认不存在才继续申请新密钥 |
| 已确认移除，尚未申请新密钥 | 查询确认无其他验证器后申请一次 |
| 新密钥申请结果未知，未收到密钥 | 停止自动修改，需要人工核对 |
| 已保存新密钥，尚未发起激活 | 发起一次激活 |
| 激活结果未知 | 查询新验证器；确认启用才保存，不再次提交激活 |
| 已核实启用，但凭据保存未完成 | 恢复本地加密保存和读回，不再次修改远端 |

如果记录中的网页登录会话已失效，或远端验证器与记录冲突，需要在账号安全设置中人工核实。恢复弹窗允许填写当前有效密钥并勾选核实确认；此操作只替换本地凭据，显示“已保存人工核实的当前 2FA 密钥”，不声称自动验证了远端状态

未完成时，账号的重新登录、重新授权、凭据覆盖、原始信息导出和删除被阻止，避免使用旧密钥或丢失恢复材料。成功后同邮箱任务统一使用新密钥。任务轮询和日志不返回恢复密钥、验证码或会话；主动导出原始信息会包含当前已保存的密钥

## 持久化边界

- 恢复记录位于数据目录的 `totp-rotations/`，使用 AES-256-GCM、邮箱绑定和独立密钥；密钥与密文必须一同备份
- 修改前先同步写入操作阶段，新密钥在激活前加密落盘；不把它放到前端存储或旧的明文设置结果文件
- 凭据保存后读回一致，才完成操作；完成后清除恢复记录里的临时密钥与登录会话
- HTTP 安全修改禁用重试、重定向与自动重放；TLS 路径使用新连接，避免旧连接断开后自动重发
- 控制台退出时停止协议子进程；意外断开 IPC 时子进程退出，重启不会自动重放未完成操作
- 单服务实例使用同一数据目录；不支持多个控制台进程并发写入同一份数据

数据库迁移不是此功能的前提，但加密记录不能消除远端请求结果未知。删除恢复目录、丢失配套密钥或手工修改数据都无法由应用自动修复

## 验证范围

`npm run test:rotation` 使用合成账号和本机模拟 HTTP 服务，验证状态机、实际协议子进程、控制台持久化和重启恢复。`npm run check` 同时覆盖原登录流程与传输层单次请求策略

当前实现参考 [Cengyj/toSub2](https://github.com/Cengyj/toSub2/tree/9a517d442b9af4e6b56ddce616fc90814cc9276f)，调用 ChatGPT 网页使用的账号安全接口。模拟测试不能证明真实服务当前可用，也不能代替真实测试账号的登录、更换与使用新密钥再次登录验收
